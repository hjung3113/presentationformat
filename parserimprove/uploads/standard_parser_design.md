# 표준 로그 파서 (Standard Log Parser) 설계 문서

> 작성 목적: 「반도체 설비 이벤트 로그파서 개선 프로젝트」의 책임 분리 구조 중 **표준 로그 파서** 컴포넌트를 아키텍처 레벨로 정의한다. 이 컴포넌트는 컨버터와 함께 올해 MVP의 핵심 가공 로직이다.
>
> 근거: 상위 문서 `parser_project_revised.md`(3.1③, 2.3, 5장), 짝 문서 `converter_design.md`·`scheduler_design.md`·`integration_contracts_design.md`. 충돌 시 상위 문서 우선.
>
> ⚠️ **본 문서는 아키텍처·계약 레벨의 골격이다. 세부 구현(하위 모듈 내부 알고리즘·필드·규칙 표현)은 확정되지 않았고 변경될 수 있어 의도적으로 생략한다.**

---

## 0. 한 줄 정의

> **표준 로그 파서는 표준 로그(및 컨버터를 거친 비표준 로그)를 분석 가능한 정형 데이터로 가공한다. 도메인 내부에 값 정규화·보정·start/end 병합 하위 모듈을 두되, 외부에는 하나의 파서로 호출된다.**

비표준도 컨버터를 거쳐 표준 형식이 되면 이 파서 하나로 처리된다(파서 일원화). 흩어져 있던 값 정규화·보정 로직(상위 문서 2.3)을 이 도메인 내부로 모으는 것이 핵심이다.

---

## 1. 배경

- 표준 로그라도 결함이 많아, 가공 전 **값 정규화**(제각각 표현 통일)와 **보정**(누락 보강·오류 교정)이 필요하다(상위 문서 2.3).
- 기존에는 이 로직이 DB·보정모듈·가공모듈 등 여러 곳에 예외처리로 산재해 버그 추적이 어려웠다. 모델별·설비사별 보정 로직만 50종 이상.
- 목표: 이 로직들을 표준 파서 도메인 내부의 하위 모듈로 정리해 단일화한다.

---

## 2. 책임 경계

### 2.1 하는 일 (In Scope)

| 책임 | 설명 |
|------|------|
| **표준 로그 가공** | 표준 로그(및 컨버터 산출 표준형)를 분석 가능한 데이터로 가공. |
| **값 정규화** | 설비사·모델별 제각각 표현(alias·코드·모듈타입)을 표준 형태로 정렬. |
| **보정** | 흐름 추적으로 누락 정보 보강 + 잘못된 값 교정. (값 정규화와 별개 단계) |
| **start/end 병합·흐름 추적** | 시작/종료가 다른 라인·파일에 나뉜 동작을 하나로 병합. |
| **carryover 처리** | 파일 경계에서 미완료 동작·흐름 정보를 이월·수신. |
| **결과·상태 적재** | 가공 결과를 DB에 적재하고, 진행상태(SSOT)·carryover를 갱신. |

### 2.2 하지 않는 일 (Out of Scope)

| 비책임 | 누가 | 이유 |
|--------|------|------|
| 비표준 → 표준 형식 변환 | 컨버터 | 형식 변환은 컨버터 몫. 파서는 표준 형식만 받는다. |
| 원본 수집·존재 확인 | 수집기 | |
| 시나리오 판단·구간 산정 | 스케줄러 | 파서는 "주어진 입력 구간을 가공"만 함(시나리오 불가지). rework의 삭제/재적재는 스케줄러가 DB에서. |

---

## 3. 내부 하위 모듈 (개념 골격)

외부에서는 하나의 표준 로그 파서로 호출되지만, 내부는 단계별 책임을 분리해 배치한다.

```mermaid
flowchart LR
    IN[표준형 입력 + 이전 carryover] --> P[파싱]
    P --> N[값 정규화]
    N --> M[start/end 병합·흐름 추적]
    M --> C[보정 - 보강·교정]
    C --> L[결과 적재 + 진행상태·carryover 갱신]
```

- 각 단계는 독립 하위 모듈. 값 정규화와 보정은 **층위가 다른 별개 단계**로 유지(상위 문서 2.3).
- 단계 순서·경계는 아키텍처 의도이며, 세부 알고리즘·규칙 표현은 구현 시 확정(본 문서 범위 밖).

> 보정 로직은 이상적으로 전담 모듈(`corrector`)로 모은다. 가공 로직 안에 예외처리로 새어 들어가지 않도록 하는 것이 이 설계의 목적이다.

---

## 4. 입출력 (계약 레벨)

| 구분 | 내용 | 계약 |
|------|------|------|
| **입력** | 표준형 로그(표준 로그 또는 컨버터 산출), 이전 파일의 carryover, 가공 대상 구간 | 표준 로그 스펙(`contracts/log-specs/`) |
| **참조** | 값 정규화·보정에 필요한 기준정보, 규칙 카탈로그 | `contracts/reference-data/`, `contracts/normalization/` |
| **출력** | DB 결과 적재 + 진행상태(watermark)·carryover 갱신 | `contracts/state/`, DB 스키마 |

- 언어: **.NET**. DB 적재는 .NET 드라이버로 직접(`integration_contracts_design.md` §2⑤).
- 시나리오 정보는 입력에 들어오지 않는다. "이 입력 구간을 가공하라"만 받는다.

---

## 5. carryover 처리 (파일 경계)

- 로그가 시간단위로 분리되어 start/end가 다른 파일에 나뉠 수 있다. 파서는 이전 파일의 carryover를 받아 병합을 완성하고, 이번 파일의 미완료분을 다음으로 이월한다.
- carryover의 저장 위치·표준/비표준별 방식·재처리 시 처리는 미정(상위 문서 10장, `contracts/state/`). 파서는 계약된 형태를 읽고 쓴다.

---

## 6. 테스트 (핵심)

- **골든 파일(동등성) 테스트**: 실제 로그 입력에 대해 기존 파서 출력 vs 신규 출력 diff — 전환 검증의 안전망(상위 문서 5.1).
- **값 정규화·보정 데이터 기반 테스트**: 50종+ 케이스를 코드가 아니라 (입력, 기대출력) 쌍으로 관리하는 파라미터화 테스트(상위 문서 5.4, `contracts/normalization/`).
- 하위 모듈별 단위 테스트(작은 함수·의존성 주입).

---

## 7. 범위 및 단계 계획

- **올해 (MVP)**: 신규 핵심. 값 정규화·보정 포함해 "표준화된 로그를 가공"하는 경로를 실제 데이터로 끝까지 동작시키고 골든테스트로 검증(상위 문서 9.1). 흩어진 주요 정규화·보정 로직을 도메인 내부로 모으는 착수.
- **차후**: 정규화·보정 케이스 커버리지 확대, carryover 중앙화, 성능 최적화.
