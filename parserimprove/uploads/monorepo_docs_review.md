# 모노레포 문서군 적대적 리뷰 (종합)

> 목적: 초안으로 작성된 "데이터 파이프라인 모노레포 문서군"을 5개 전문가 페르소나로 적대적 리뷰한 결과를 아카이빙한다. 세부 구현이 아니라 **전체 형식·속성·프로젝트 적합성** 위주.
>
> 리뷰 대상 실제 프로젝트: 반도체 설비 이벤트 로그파서 개선(온프렘 AP서버→DB, TSV 실시간 로그, 폴리글랏 .NET/Python). 관련 설계문서: `file_collector_design.md`, `scheduler_design.md`, `integration_contracts_design.md`, 상위 `parser_project_revised.md`.
>
> 리뷰 페르소나: ① 데이터 플랫폼 아키텍트 ② 모노레포·DevEx 스태프 ③ DataOps·오케스트레이션 ④ 문서·정보 아키텍트 ⑤ 도메인 적합성 회의론자.

---

## 한 줄 결론

초안 문서군은 **클라우드 데이터웨어하우스 배치 ETL 데이터계약 모노레포 템플릿**(S3/parquet/Spark, raw→mart 계층, payment/user 예제, producer-consumer DAG, dataset별 freshness SLA, dashboard/ML consumer)을 거의 그대로 이식한 것이다. 우리 도메인과 **골격 6개가 정면 충돌**하고 **도메인 핵심 7개는 자리조차 없다**. 5명 중 4명이 "대폭 개조", 1명이 "폐기 후 재작성"을 권고 — 사실상 만장일치로 *현 상태 채택 불가*.

## 페르소나별 고유 기여

- **① 데이터 플랫폼 아키텍트**: SSOT 이중 충돌 — 문서는 `contracts/`를 SSOT라 하는데 실제 SSOT는 "설비별 진행상태 DB". watermark/carryover 경계가 계약에 없음.
- **② DevEx 스태프**: 삼중 미스매치 = *컨텐츠 부적합 + 프로세스 과함 + 강제수단 부재*. `libs/` 공유정책에 NuGet vs pip 언어별 구분 전무. contract 스키마 자체도 이미 불일치(`- pipeline:` vs `- consumer:` 혼용).
- **③ 오케스트레이션**: **backfill을 "따라잡기"로 오인할 위험** — 둘은 트리거·우선순위·자원정책·carryover가 전혀 다름. probe→collect 제어 루프, 멱등성/재개지점/락 부재. "duplicate producer 금지"는 오히려 큐+워커(KEDA) 방향과 충돌.
- **④ 문서·정보 아키텍트**: **breaking-change 목록이 4개 문서(02/06/07/README)에 갈라진 채 이미 drift 시작**. 07(영어)/09(한국어) 거의 동일. 인덱스·소유·용어집·외부설계문서 링크 4대 공백. **11개 → 6개 통합 가능**.
- **⑤ 도메인 회의론자**: raw→mart 계층·dashboard/ML consumer·dt=date 일파티션이 사고틀을 지배 → 에이전트가 "일 단위 집계 테이블"을 만들려 함. **carryover는 일파티션 모델로는 표현 자체가 불가능**.

## 의견 차이와 판정: 개조 vs 폐기

"개조 vs 폐기"가 갈렸으나 실질은 같은 곳으로 수렴한다. 부적합 비율이 커서 **파일 단위 개조는 남의 골격에 우리 개념을 끼워맞추다 오독(mart 계층·SLA·승인절차)을 상속**하게 된다. 그러나 도메인 무관한 **메타 원칙 4개는 진짜 자산**이며 이미 우리 설계문서에 부분 구현돼 있다.

> **결정: 템플릿 콘텐츠는 버리고, 아래 4개 원칙 + 모노레포/계약-우선 구조만 재사용해 도메인 문서군을 새로 작성.**

살릴 메타 원칙:
1. 경로·설정을 코드에 하드코딩 말고 ID/계약으로 관리
2. 산출물마다 owner + 명시적 계약
3. 변경 영향도를 PR에서 점검
4. 에이전트가 코드보다 계약을 먼저 읽는 contract-first 지침 구조

## 실행 매핑

**버릴 것** — S3/parquet/Spark storage 모델, raw/mart 계층, producer-consumer DAG를 스케줄링 SSOT로 삼는 전제, dataset별 freshness SLA, dashboard/ML/finance consumer, versioned dataset/deprecation 승인절차, payment/user 예제 전부, `s3://` 하드코딩 린터.

**남길 것(경량화)** — 위 4원칙, owner 명시, 슬림한 PR 영향도 점검, contract-first 에이전트 읽기순서, "산출물은 id를 갖는다"는 계약-우선 발상.

**새로 넣을 것** — 계약 대상을 도메인으로 재정의: **표준 로그 스펙(TSV 스키마) · 값 정규화·보정 규칙 카탈로그 · 기준정보(설비/모델/메이커) 마스터 · 설비별 진행상태+carryover(DB SSOT) · 골든파일 세트**. 그리고 **폴리글랏 경계(.NET↔Python)**, **스케줄러 실제 모델(설비 팬아웃+시나리오+CPU 평준화+probe/collect)**, **Config 파서 컴포넌트**, **온프렘 AP서버→DB 토폴로지**.
