## 1. 요약 — 무엇을, 왜 지금, 무엇이 드는가
- intent: 첫 화면에서 요청·비용·되돌리는 방법·왜 지금을 모두 보인다. 요청은 작고(준비 2주) 되돌리기 쉽고(Jira 그대로), 새 예산이 없다
- shape: headline-metric
- payload: 리드(이 순서로): 요청은 하나다 — 이미 만든 VOC·Task 도구(FeedbackOps)를 한 팀에서 실제로 써 보고 지금 Jira 처리와 숫자로 비교해 확대 여부를 다시 올린다 [F79]. 오늘은 그 준비 2주만 승인을 구한다 — 기준선 추출, 보안 사전 확인, 시범 팀 동의, 사내 로그인·인프라 협조 요청, 병행 기간 접수 경로 확정 [F79]. 운영 8주는 2주 뒤 기준선 숫자와 함께 다시 올린다 [F71]. 시범 동안 Jira 접수는 그대로 두므로, 기준에 못 미치면 그 팀이 FeedbackOps 사용을 멈추는 것으로 끝난다 [F77]. 새 예산 요청은 없다 — 서버 비용은 인프라 회신 뒤 보고 [F78]. 드는 것은 사람 시간이다: 사내 로그인·인프라 담당의 협조, 시범 팀의 병행 운영, 발표자 시간(비율은 D3에서 정한다) [Q02]. 지금인 이유: 두 시스템 모두 사내 연결 직전까지 와 있지만, 다음 단계는 사내 회신과 보안 확인 없이는 진행할 수 없어 지금은 가짜(시험용) 데이터 위에 머물러 있다 [F06][F14][F15]. 타일 4개(강조 타일 없음): VOC→Task→문의자 통지 = 구현, 개발 묶음 32개 중 31개 완료·사용자 매뉴얼 0–12장 [F06][F07]; 팀장용 할 일 목록 = 6종, 미배정 VOC·심각한데 작업에 안 이어진 VOC 등 [F26]; 사내 로그인(SSO)이 선행 조건인 작업 = 4건, 실제 데이터 연결·권한·시험 서버·플랫폼 서버 [F12]; 사내 실서버 검증 = 0건(문제 변형), 시범의 첫 목표 [F15]. 타일 아래 한 줄('만든 방식'): 두 시스템은 발표자 1인이 AI 코딩 에이전트와 함께 만들었다(플랫폼은 레포 생성부터 v0.2.0까지 18일). 그래서 검증을 자동 검사로 강제했다 — 플랫폼 자동 검사 54개, 테스트 코드가 제품 코드보다 많다(1.07배·1.4배). 다만 FeedbackOps에는 아직 CI가 없고 남는 위험은 1인 의존이다 [F01][F03][F04][F05][F43][F45]. 핵심 콜아웃(상사에게 할 한 줄, KEY): 이미 만든 VOC·Task 도구를 한 팀에서 시범한다 — 오늘은 준비 2주만, 예산 요청 없이 Jira는 그대로 두고, 2주 뒤 기준선 숫자로 운영을, 12주 뒤 확대 여부를 다시 올린다.

- shape: before-after
- payload: 리드 첫 문장: Jira에 VOC는 남지만, 어떤 VOC가 어떤 작업으로 이어졌고 문의자에게 알렸는지는 남지 않는다(소유자 진술 — 준비 단계의 Jira 추출로 숫자 확인) [F50][F55][F56][F57][F75]. 지금: VOC 사이 후속 공유·여러 VOC를 묶어 작업으로 만들기·처리를 성과로 보이기가 어렵다 [F55][F56][F57]; 작업 관리는 시스템이 사실상 없다 [F51]; CLAS는 공통 기반 없이 메뉴를 합친 형태 [F53]; 공지·설문이 부족하다 [F54]; 분석 앱 하나는 EES에 묶인 데스크톱 앱이라 개발 자유도가 낮다(이번 시범 범위 밖) [F52][Q05]. 목표: 하나의 기반 위에 업무 메뉴 6갈래가 얹히고 메뉴 사이가 이어진다 — 운영 지원(VOC·설문·공지), 개발 지원(작업), 생산성 분석, 기준정보, 모니터링, 표준로그 개발 관리(미설계) [F59][F37]. ## 4. 목표 흐름 — 문의자·담당·팀장이 각각 얻는 것
- intent: 같은 VOC를 문의자·담당 개발자·팀장이 각자 필요한 모양으로 보는 흐름을 보이고, 팀장에게 직접 이로운 기능을 앞으로 꺼낸다
- shape: role-handoff
- payload: 문의자가 VOC를 올린다(분석 화면 문맥을 넘기는 등록은 계획) [F30][F31]. 담당 개발자가 같은 문제의 VOC를 묶음(클러스터)으로 모은다 [F24]. 묶음에서 작업 요청을 올리고, 팀장이 승인한 뒤에만 작업이 된다 — "작업 관리가 없다"는 문제에 대한 직접적인 답 [F25][F51]. 처리·릴리스되면 공개 업데이트 검토 후보가 생기고 [F28], 묶음 전체에 공개 업데이트를 한 번 보낸다 [F24]. 문의자는 '내 VOC'에서 8단계 상태와 연결된 작업을 직접 본다 [F23]. 팀장이 얻는 것(흐름 아래 목록): 팀장 화면은 차트가 아니라 할 일 목록이다 — 미배정 VOC, 심각한데 작업에 안 이어진 VOC, 판단만 하고 실행이 없는 건, 릴리스됐는데 문의자 쪽이 안 끝난 VOC, 결과가 나쁜데 후속이 없는 건, 권한 요청 대기 [F26]; 분기 보고에는 VOC→작업 연결률과 릴리스 후 통지율을 숫자로 쓴다 [F27]; 담당자는 문의자에게 말 없이 상태만 바꿀 수 없다 — 공개 업데이트나 건너뛴 이유가 남는다 [F22]. 각주: 회의에서 가짜 계정으로 5분 시연(제안) [F48]; 등록 문맥 전달을 뺀 흐름은 FeedbackOps에 구현돼 있고 사용자 매뉴얼 0–12장이 있다 [F06][F07].

## 5. 하나의 기반 — 두 시스템의 관계와 왜 하나인가
- intent: 왜 시스템이 둘이고 왜 합치며 왜 지금은 안 합치는지를 3줄로 먼저 풀고, 업무 6갈래를 따로가 아니라 하나의 기반에 얹는 이유와 갈래별 실제 상태를 숨기지 않고 보인다
- shape: layered-structure
- payload: 두 시스템의 관계(카드 3장, 그림 앞): 지금 — FeedbackOps(VOC·작업·설문)를 먼저(2026-05-16 첫 단계 완료) 만들었고, 다른 업무 메뉴까지 얹을 바닥으로 플랫폼을 만들었다. 두 시스템은 따로 돌고, 플랫폼에서 '내 VOC·설문'을 읽어 FeedbackOps로 넘어가는 연결은 대부분 끝났다(같은 사내 로그인 전제) [F47][F19]. 시범 — 이미 완성된 FeedbackOps로 VOC 효과부터 잰다. 합치는 비용을 쓰기 전에 효과를 먼저 확인하기 위해서다 [F79]. 판정 통과 뒤(별도 결정) — FeedbackOps 화면을 플랫폼 메뉴로 옮겨 사용자는 한 곳에서 쓰고 서버는 FeedbackOps 것을 그대로 쓴다. 플랫폼이 이미 FeedbackOps의 디자인·부품을 쓰고 있어 새로 만드는 일이 아니다. 거친 추정 4~8주, 일정 승인 아님 [F16][F20][F17]. 왜 하나인가(리드): 메뉴마다 따로 만들면 반복되는 것 — 로그인·권한·변경 감사·메뉴 활용률·표 내보내기·필터 — 를 플랫폼이 한 번만 만든다. 실제로 견본 메뉴 3곳이 내보내기를 각자 만들다 한 곳은 엑셀 한글이 깨졌고, 필터는 5곳이 각자 만들었다 [F08][F09]. 팀장은 메뉴 활용률로 어떤 메뉴가 실제로 쓰이는지 숫자로 본다 [F49]. 메뉴 사이 연결의 한 장면: 사이클타임 이상 → 느린 실행 → 실행 상세 → 그 문맥 그대로 VOC 등록 — 분석 화면은 있으나 가짜 데이터, 문맥 넘기기는 계획 [F30][F31][F32]. 성공 기준: 새 메뉴를 얹을 때 플랫폼 코드를 고치지 않는다 [F10][F11]. 갈래별 상태(그림): 화면 있음(가짜 데이터) — 생산성 분석 3화면, 지표, 설비 조회, 운영 콘솔(권한·감사·활용률) [F32][F33][F34][F35]; 별도 앱으로 구현 — VOC·설문·작업(FeedbackOps) [F06]; 대기·예정·미설계 — 시스템 모니터링(대기), 공지(예정), 공정·레시피 기준정보(예정), 표준로그 개발 관리(미설계) [F35][F36][F34][F37]. 플랫폼 공통 기반은 구축 [F40][F41]. 데이터·로그인은 사내 회신 대기 — 사내 로그인(SSO), 플랫폼용 사내 서버, FeedbackOps 서버는 그대로 [F12][F13][F16].
