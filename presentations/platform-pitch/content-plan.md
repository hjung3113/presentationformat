## 2. 지금의 문제 — VOC가 성과로 남지 않는 구조
- intent: 문제는 사람의 노력이 아니라 흩어진 도구라서 처리한 일이 기록과 성과로 이어지지 않는다는 것을, 지금과 목표로 대비한다
- shape: before-after
- payload: 지금(모두 소유자 진술): VOC는 Jira로 받지만 VOC 사이 후속 조치 공유, 여러 VOC를 묶어 Task로 만들기, 처리를 성과로 보여 주기가 어렵다 [F50][F55][F56][F57]. Task 관리는 시스템이 사실상 없다 [F51]. 분석 앱 하나는 EES에 묶인 데스크톱 앱이라 개발 자유도가 낮다 [F52]. CLAS는 공통 기반 없이 메뉴를 합쳐 놓은 느낌이다 [F53]. 공지·설문이 부족하고 나머지도 흩어져 있다 [F54]. 목표: 하나의 기반 위에 업무 메뉴가 얹히고, VOC → 클러스터 → Task Request → Task → 문의자 통지가 한 흐름으로 이어지며, 관리자는 연결률로 성과를 본다 [F24][F25][F27][F59]. Jira 전체를 대체하지 않는다 — VOC 흐름만 옮겨 시험한다 [F29].

## 3. 목표 흐름 — 문의에서 성과까지, 누가 무엇을 보나
- intent: 같은 VOC를 문의자·담당 개발자·팀장이 각자 필요한 모양으로 보는 흐름을, 이미 구현된 것과 계획인 것을 구분해 보여 준다
- shape: role-handoff
- payload: 문의자가 VOC를 올린다 — 분석 화면의 문맥을 그대로 넘기는 등록은 계획(#81) [F30][F31]. 담당 개발자가 같은 문제의 VOC를 클러스터로 묶는다 [F24]. 클러스터에서 Task Request를 올리고, 팀장(검토자)이 승인한 뒤에만 Task가 된다 [F25]. 처리·릴리스되면 공개 업데이트 검토 후보가 생기고 [F28], 담당 개발자가 클러스터 전체에 공개 업데이트를 한 번 보낸다 [F24]. 상태를 바꿀 때는 공개 업데이트나 건너뛴 이유가 남는다 [F22]. 문의자는 '내 VOC'에서 8단계 상태와 연결된 Task를 직접 본다 [F23]. 팀장은 행동 큐 6종과 연결 지표로 처리와 성과를 본다 [F26][F27]. 등록 문맥 전달을 뺀 나머지는 FeedbackOps에 구현돼 있고, 실사용 배포는 사내 SSO가 선행 조건이다 [F21].
