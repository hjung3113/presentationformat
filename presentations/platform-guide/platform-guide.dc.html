01 · LAYERS

층과 의존 방향 — 메뉴가 쓸 수 있는 것

패키지는 다섯 층으로 나뉘고 import는 한 방향으로만 흐른다. 의존 방향은 contracts → ui·kernel → components → shell → apps이다. 역방향 import는 경계 lint가 막는다. 메뉴 패키지(@ap/menu-<group>)는 그룹당 하나씩 모두 7개다. 이 패키지는 contracts·kernel·components·ui 네 개만 import할 수 있고, 다른 메뉴로는 linkTo로만 간다. mock-server는 개발 전용이라 Kernel·components·shell은 mock을 모른다.

02 · REGISTRY

공간·그룹·메뉴 — 사이드바가 만들어지는 방식

사이드바와 breadcrumb는 코드가 아니라 공간(Space) → 그룹 → 메뉴 manifest로 이어지는 선언으로 만든다. 플랫폼 UI 계약 문서(06)는 공간을 셋으로 정했지만, 지금 SPACES에 등록된 것은 분석과 운영 콘솔 둘이다. 피드백 공간은 M5, 곧 FeedbackOps 화면 이전(2단계) 때 등록할 예정이다. 소속 공간은 메뉴가 아니라 그룹이 GroupDef.space로 선언한다. 그룹 7개에 걸린 manifest 17개 가운데 화면이 있는 것은 13개다. 새 메뉴를 더해도 사이드바와 breadcrumb 코드는 고치지 않는다. 잘못된 선언은 createRegistry가 시작할 때 위반 16종(id·경로 충돌, primary 1개 규칙 등)을 기준으로 거부한다.

03 · ARCHETYPES

화면 유형 5종 — 페이지의 뼈대

모든 메뉴 화면은 manifest의 pageType으로 화면 유형 5종 중 하나를 고른다. 유형마다 콘텐츠 슬롯 이름이 정해져 있다(합계 27개). Page Header와 Global Context는 셸 슬롯이다. PlatformPage가 이미 그리므로 뼈대에 다시 넣지 않는다. 지금 pageType이 강제하는 것은 값 자체와 생성기가 만드는 뼈대의 슬롯 이름뿐이다. 공통 레이아웃 컴포넌트는 ManagementLayout과 AnalysisLayout 둘뿐이다. Workflow 유형은 아직 쓰는 메뉴도, 공통 레이아웃도 없다.

04 · SURFACE

화면 한 장의 구역 — 누가 무엇을 그리나

관리 화면 한 장은 여섯 구역으로 나뉜다. 전역 Context Bar는 셸이 그린다. 페이지 머리와 Scope 게이트, 같은 응답을 하나로 모은 배너는 PlatformPage가 자동으로 그린다. 그래서 메뉴는 날짜·Scope 선택기를 따로 만들지 않는다. 메뉴가 채우는 것은 ManagementLayout의 filter·table·drawer 슬롯이다. 조회 결과가 ok가 아니면 QueryView가 본문 자리에 결과별 상태 화면을 낸다.

05 · DATA FLOW

데이터가 오는 길 — 선언 하나, 포트 하나

메뉴 데이터는 선언 → 조회 → 포트 → 서버 순서로 흐른다. 메뉴는 endpoints.ts에 defineEndpoint로 권한과 적용 Context, params, assessment kind, 한도를 선언한다. 화면은 이 선언을 useMenuQuery로 읽는다. 모든 조회는 PlatformAdapter의 menuQuery 하나로 가므로, 새 메뉴를 만들어도 포트 메서드는 늘리지 않는다. 서버는 요청에 실린 값이 아니라 자기가 가진 선언 사본으로 판정한다. 판정은 요청 모양 → params → 권한 → Scope → 한도로 시작하는 10단계이고, 그 순서도 계약이다.

07 · NAVIGATION

메뉴 사이 이동 — Context를 들고 가는 링크

플랫폼의 핵심 가치는 메뉴 수가 아니라 Context를 들고 이동하는 데 있다. 이동에는 linkTo(menuId, { params, page, global, returnTo })를 쓴다. 이때 목적지 ID(params)와 Context(global)를 섞지 않는다. 목적지가 지원하지 않는 Context는 버리지 않고 '이 화면에서 미사용'으로 표시한다. 아래 사슬은 실행 상세까지 견본 메뉴에 구현돼 있다. 마지막 단계인 'VOC 생성(현재 Context와 함께)'은 아직 없어서, 실행 상세의 버튼은 'VOC 생성(예정)'으로 나온다.

08 · PERMISSIONS

  • 입력창 3개 — 진행 안내(Public Update)와 문의자 답장(Reporter Reply), 내부 코멘트(Internal Comment)는 서로 섞이지 않는다. 진행 안내는 문의자에게 보이는 유일한 창구이고, 내부 코멘트는 문의자에게 보이지 않는다.
  • 작업 요청 — 검토되지 않은 후보가 백로그를 채우지 않게 막는다(상태 5개). 같은 문제를 말하는 VOC는 묶음(클러스터)으로 모은다. 묶음은 draft로 시작해 confirmed가 된다.
10 · MIGRATION

FeedbackOps 이전 — 화면은 옮기고 백엔드는 둔다 (계획)

FeedbackOps는 2단계로 플랫폼에 들어온다. 1단계(연결)는 독립 앱을 그대로 두고 공유 SSO·디자인·딥링크로 잇는 방식이며, 2026-09-26에 정해 대부분 끝났다. 2단계인 화면 이전은 2026-10-04에 정한 A안대로 진행할 계획이다. A안은 화면을 menus/feedback-*로 옮기고, 백엔드는 FeedbackOps 도메인 API로 둔다. 앱 통째 마운트(B)와 백엔드 재작성(C)은 기각했다. 화면 이전에 드는 기간은 4~8주(추정)이고, 이 값은 일정 승인이 아니다. 디자인은 @ap/ui가 @fops/ui를 재수출해 이미 공유한다.
