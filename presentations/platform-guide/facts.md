## 요약

- 의존은 한 방향이다. `contracts → ui/kernel → components → shell → apps`이고 메뉴는 contracts·kernel·components·ui만 쓴다. 메뉴끼리 import할 수 없고 이동은 `linkTo`뿐이다. 경계는 lint(프리셋 10개, 커스텀 규칙 5개)가 막는다.
- 메뉴는 manifest 선언만으로 얹힌다. 지금 manifest 17개 중 화면이 있는 것은 13개, 계획 메뉴 4개는 '예정'으로 보인다. 공간은 분석·운영 콘솔 2개만 등록돼 있고 피드백 공간은 M5 뒤다.
- 화면은 `PlatformPage` 위에 5 Page Archetype 중 하나를 얹는다. 공통 레이아웃은 Management와 Analysis 두 개뿐이고 Workflow는 쓰는 메뉴도 레이아웃도 아직 없다.
- 데이터는 `endpoints.ts` 선언 → `useMenuQuery` → 포트 메서드 `menuQuery` 하나다. 새 메뉴는 포트 메서드를 늘리지 않고, 서버는 요청이 아니라 자기 선언 사본으로 권한·Scope·한도를 판정한다.
- 지금 서버는 mock뿐이다. 실어댑터(#154)와 FastAPI(#155)는 저장소에 없고, 운영 조립은 `AP_PLATFORM_ASSEMBLY`로 꽂으며 운영 빌드에 mock이 섞이면 빌드가 실패한다.
- 메뉴 하나는 7단계(시작 전 → 그룹·패키지 → 조회 선언 → 화면 → 서버 쪽 → 적합성 묶음 등록 → 검증)로 만든다. `pnpm gen:menu`는 새 그룹의 스켈레톤(파일 11개+앱 배선 6줄)만 만들고 `--remove`는 수정 안 한 스캐폴드만 되돌린다.
- 메뉴 개발자가 하지 않는 것은 `packages/*` 수정, 포트 메서드 추가, 메뉴 간 import, URL 직접 조립, 화면의 권한 판단, wall-clock의 TZ 변환이다.
- 권한은 8개 키이고 서버가 매 요청 재검증한다. Scope는 단일 Site이며 `null`은 "전체 사이트"가 아니라 거부다. 클라이언트의 `can`·`allowed`는 표시 힌트이고 E2E는 서버 거부를 관찰하지 못한다.
- FeedbackOps 흐름의 핵심은 상태 분리다. 리포터 상태 8단계·내부 트리아지·Task 상태 7개는 서로 자동 연동되지 않고, 공개 업데이트·리포터 답장·내부 코멘트는 입력창이 셋이며, Task `released`는 공개 업데이트 검토 후보만 만든다.
- FeedbackOps 이전(A안)은 화면만 `menus/feedback-*`로 옮기고 백엔드는 도메인 API로 남는다. 디자인은 이미 `@fops/ui` 재수출로 공유하지만 쓰기 계약·Workflow 레이아웃·세션 공유 결정이 선행 과제로 남아 있다.
