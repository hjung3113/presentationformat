FeedbackOps 설계 브리프
흔적이 이어지는 피드백 운영

FeedbackOps는 VOC·설문·실행·효과 검증을 하나의 거대한 워크플로로 합치지 않는다. 각 시스템이 혼자서도 완결되게 두고, 필요한 순간에만 근거와 실행의 연결을 감사 가능한 이력으로 남긴다.

본 문서는 승인 요청서가 아니라, 시스템 구조와 핵심 흐름을 공유하는 설계 설명 자료이다.

01 · CONTEXT

운영 맥락 — 흩어진 피드백 흔적

피드백 운영의 비용은 VOC를 받는 일보다, 그 VOC가 어떤 판단과 실행으로 이어졌는지를 나중에 설명하는 일에서 더 크게 생긴다. 접수·트리아지·근거 수집·실행 추적·결과 검증이 서로 다른 도구에 흩어져 있으면 그 흔적은 사람이 손으로 재구성해야 하고, FeedbackOps는 이 흔적을 entity_links 하나에 정본으로 남겨 감사 가능한 운영 자산으로 만든다.

02 · ARCHITECTURE

시스템 구조 — 독립 시스템과 선택적 통합 계층

VOC·Survey·Task는 각자 혼자서도 완결되는 업무 시스템이고, 시스템 사이 연결은 필수 흐름이 아니라 선택 기능이다. Finding·Entity Link·Action Dashboard를 담은 Integration Layer가 필요한 순간에만 근거와 실행을 잇고, 그 아래 Core Platform이 Workspace·Managed System·권한을 공통으로 맡는다.

03 · TRIAGE

VOC 트리아지 — Task까지 가지 않는 결말

새 VOC는 Untriaged로 들어오고, 담당과 심각도·분류를 정한 뒤 후속 경로를 다섯 갈래 중 하나로 결정한다. VOC는 Task를 만들기 위한 입력 양식이 아니므로, 공개 업데이트만 하거나 후속 없이 종료하는 것도 사유가 기록되는 정당한 결말이다.

04 · HANDOFF

실행 요청 인계 — 요청자·검토자·실행 담당

후속 실행은 Task를 바로 만들지 않고 Task Request라는 완충 객체를 거친다. 요청자가 근거와 함께 실행 후보를 올리면 같은 범위의 검토자가 판단하고, 승인된 요청만 Convert to Task로 Backlog Task가 되어 실행 담당에게 넘어간다.

05 · LIFECYCLE

Task Request 상태 — 승인과 전환의 분리

Task Request는 검토 대기에서 출발해 승인·반려·근거 보완 요청 중 하나로 갈리고, 승인된 요청은 새 Task로 전환되거나 기존 Task에 연결될 때까지 승인 상태로 남는다. 모든 결정은 감사되며, 이 상태는 작성자에게 보이는 VOC 상태와 자동으로 연동되지 않는다.

06 · LINKING

연결 모델 — entity_links 하나로 모이는 교차 이력

시스템 사이 관계는 각 객체가 외래키로 직접 소유하지 않고, source·target·relation_type·visibility를 담은 core.entity_links 한 곳에 정본으로 남는다. 링크를 해제해도 행을 지우지 않고 detached로 남기므로, "무엇을 근거로 무엇을 했는가"는 언제든 되짚을 수 있다.

07 · INVARIANT

금지된 변환 — 설문 응답은 VOC가 되지 않는다

VOC는 사내 AD로 인증된 사용자가 직접 제출한 목소리만 담는다. 그래서 설문 응답을 새 VOC로 바꾸는 지름길은 막혀 있고(generated_voc는 금지 관계), 설문 결과는 Finding·Task Request의 근거로 연결되거나 기존 VOC에 첨부된다.

09 · SCOPE

출시 범위 — Alpha에서 Phase 2까지

Alpha가 Core·권한·VOC·Entity Link의 바닥을 깔고, MVP가 Finding·Task Request·Action Dashboard로 근거에서 실행까지의 연결을 완성한다. 자동화·고도화는 Phase 1·2로 미루며, 출시 단계는 날짜가 아니라 범위로 정의한다.

용어

VOC — 사내 AD 인증 사용자가 직접 제출한 목소리. 설문 응답에서 만들지 않음

Managed System — MVP의 범위·필터·기본값·권한 기준이 되는 관리 대상 시스템
entity_links — 시스템 간 관계의 정본 테이블. 해제해도 이력 보존
