FeedbackOps
피드백에서 실행까지 이어지는 운영 시스템

FeedbackOps는 내부 VOC·설문·Finding·Task·결과 검증을 하나의 거대한 워크플로로 합치지 않고, 각 시스템이 독립적으로 동작하면서 필요한 순간 근거·결정·실행 이력을 연결하게 한다. 프로젝트의 핵심은 새 도구 하나가 아니라, 흩어진 피드백 운영의 궤적을 복원 가능한 운영 자산으로 만드는 것이다.

본 문서는 외부 소개용 마케팅 자료가 아니라, 프로젝트 필요성·사용 시점·시스템 연결 방식을 설명하는 설계 보고 자료이다.

01 · BACKGROUND

필요성 — 피드백과 실행 사이의 끊어진 궤적

피드백 운영에서 가장 큰 비용은 VOC를 받는 일이 아니라, 그 VOC가 어떤 근거로 묶였고 어떤 실행으로 이어졌으며 실제 효과가 있었는지를 나중에 설명하는 일이다. 기존 도구 조합은 인테이크·설문·이슈·결과 확인을 각각 처리하지만, 그 사이의 연결은 사람이 기억·회의록·수동 링크에 의존한다. FeedbackOps는 이 구간을 감사 가능한 연결로 만든다.

흩어진 인테이크

VOC와 Survey Response가 다른 표면에서 들어오고, 중복·유사·원인 판단이 개인 기억에 의존한다.

설명되지 않는 실행

Task는 존재하지만 왜 시작됐는지, 어떤 증거가 있었는지, 어떤 사용자 문제와 연결되는지 추적하기 어렵다.

닫히지 않는 검증

Task Done이 곧 사용자 문제 해결을 뜻하지 않는다. Reporter 대면 상태와 Outcome Survey가 별도 검토를 요구한다.

02 · USE CASE

사용 시점 — 피드백이 운영 업무로 전환되는 순간

FeedbackOps는 모든 대화를 저장하는 범용 CRM이 아니다. 내부 AD 인증 Actor가 관리 대상 시스템에 대한 피드백·검증·후속 실행을 운영해야 할 때 사용한다. 핵심 사용자는 PM, CX·CS Ops Manager, VOC Manager, Product Ops, Workspace Admin이며 Developer와 Survey Operator는 실행·검증 흐름에서 함께 사용한다.

2.1

VOC가 들어왔을 때

Reporter가 Managed System을 선택해 VOC를 등록한다. Admin 또는 same-scope Developer가 Inbox와 Triage에서 owner·severity·category·Analytics Area·follow-up path를 결정한다.

2.2

증거를 묶어야 할 때

단일 VOC의 조치가 명확하면 Task Request로 바로 간다. 여러 VOC·Survey 결과·수동 분석을 합쳐 판단해야 하면 Finding을 만든다.

2.3

실행 후보를 검토해야 할 때

VOC나 Finding은 Task를 직접 만들지 않는다. Task Request가 증거 요약·요청 결과·Managed System 범위를 들고 검토 큐에 들어간다.

2.4

후속 공백을 찾아야 할 때

Dashboard와 Integration은 모든 미연결 항목을 문제로 보지 않는다. 정책·severity·workflow 설정이 기대한 링크나 후속 결정이 없을 때만 recovery item으로 보여준다.

03 · SYSTEM MAP

시스템 지도 — 독립 시스템과 선택적 통합 계층

FeedbackOps의 설계는 VOC·Task·Survey를 한 시스템으로 합치는 것이 아니라, 각각 독립적으로 완료 가능한 업무 시스템으로 둔 뒤 필요한 순간 Finding·Evidence·Entity Link·Action Dashboard가 연결하게 한다. 이 분리는 제품을 작게 시작하게 하고, 동시에 운영 이력을 잃지 않게 한다.

06 · VOC BRANCH

VOC 분기 — Task까지 가지 않는 경로

VOC는 Task를 만들기 위한 입력 양식이 아니다. 트리아지 결과에 따라 정보 요청, 공개 업데이트, Finding 생성, Task Request 생성, no-follow-up-needed 결정으로 갈라진다. 실행하지 않는 결정도 이유와 감사 이력을 가진 명시적 운영 결정이다.

11 · ACCESS

권한과 신뢰 — 내부 기본 접근을 낮게 둔다

MVP 사용자는 모두 AD 인증 Actor이지만, 로그인 자체가 민감 기능 접근을 뜻하지 않는다. 기본 Role Level은 User이며, Backstage Task·개인 Survey 응답·Export·Admin 기능은 capability와 Managed System scope가 있어야 한다. Reporter는 역할이 아니라 특정 VOC를 제출한 Actor를 뜻한다.

User

본인 VOC 작성·상태 확인, 할당 Survey 응답이 기본이다. Task 내부 댓글과 Backstage에는 접근하지 못한다.

Developer

허용된 Managed System scope 안에서 VOC triage, Finding, Task Request, Task, Integration queue를 다룬다.

Admin

Permission Request, Admin configuration, workspace-wide 관리 기능을 다룬다. Explicit Deny는 일반 Allow보다 우선한다.

권한이 막힌 링크나 next action은 빈 실패가 아니라 요청 경로를 보여준다. 승인 후 사용자는 가능하면 원래 막혔던 객체나 action으로 돌아간다.
12 · OPERATION

운영 화면 — 리스트 우선, 다음 행동 우선

UI는 빠르고 밀도 높은 운영 도구를 기본으로 한다. 주요 객체는 List에서 스캔하고 Right Detail Panel에서 검사한다. Home은 내가 지금 할 일을, Dashboard는 Managed System이나 workspace가 어디서 막혔는지를, Integration은 근거·종합·실행·검증 연결이 어디서 끊겼는지를 답한다.

Home

개인 실행 큐

현재 Actor가 지금 직접 처리할 수 있는 recovery item과 assigned work를 보여준다.

Dashboard

운영 병목 큐

Managed System별 현황, follow-up gap, coverage를 보여준다. 차트는 분석보다 queue navigation을 돕는다.

Integration

연결 복구 큐

source evidence, synthesis, execution, validation이 설정된 정책대로 연결되지 않은 지점을 보여준다.

Admin

운영 기준 설정

Managed System Registry, Analytics Area, Permission Request, workspace policy를 관리한다.

13 · SCOPE

범위 — MVP가 하는 일과 하지 않는 일

MVP는 피드백 운영의 핵심 루프를 먼저 닫는다. 고급 자동화와 외부 도구 연동은 나중 단계로 둔다. 이 범위 설정은 제품을 작게 만들기 위한 축소가 아니라, 시스템 간 연결 규칙을 먼저 안정화하기 위한 선택이다.

MVP 포함

AD Login, Workspace, Managed System Registry, VOC 등록·Triage, Basic Task, Finding, Task Request, Survey Type, Entity Link, Action Dashboard 기본형을 포함한다.

MVP 제외

Survey Response → VOC conversion, full automatic clustering, custom workflow builder, advanced BI, external/customer-contact login, external tool integrations를 제외한다.
