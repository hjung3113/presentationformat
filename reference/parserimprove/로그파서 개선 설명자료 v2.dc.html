설비가 실시간으로 남기는 방대한 로그를, 사람이 분석·활용할 수 있는 정형 데이터로 바꿔 주는 핵심 데이터 파이프라인. 오랜 운영으로 누적된 구조적·운영적 부채를 점진 수선하는 대신,
 책임이 명확히 분리된 새 구조로 재설계하여 장기적인 유지보수성·확장성·운영 효율을 확보한다.

본 문서는 승인 요청서가 아니라, 실무자가 실제로 어떤 방향으로 개선을 진행할지 설명하기 위한 실행 방향 공유 자료이다. 전체 구조는 개요 수준으로 설명하되, 상세 실행 범위는 올해 MVP를 중심으로 정리한다.

01 · BACKGROUND

배경 및 개요

설비 이벤트 로그파서는 동작 단위로 로그를 묶는 것을 넘어, 설비·랏·웨이퍼의 흐름을 추적해 부족한 정보를 채우고 여러 로그를 합쳐 새 정보를 만든다. 실시간 로그는 start와 end가 서로 다른 라인·파일에 기록되므로 파서가 이를 병합해 분석 가능한 데이터로 만든다. 이 데이터가 통계·분석의 기반이 되므로 파서의 정확성은 곧 후속 데이터 신뢰도와 직결된다.

추진 배경 — 현재 파서가 부딪힌 한계

구조적 한계
수집·삭제·표준/비표준 가공·Config가 한 프로그램에 뒤섞이고 정규화·보정마저 흩어져, 유지보수와 버그 추적이 어렵다.
레거시 부채
인수인계가 미흡한 저품질 레거시에 테스트 코드도 없어, 수정·배포가 개인 경험에 의존한다.
운영 부담
재처리·따라잡기를 자동 처리하지 못해 수작업·실수가 잦고, 순간 부하 피크로 서버 오류가 난다.
변화하는 요구
설비·로그가 갈수록 복잡해지는데 현재 구조로는 따라가기 어렵고, 방치하면 한계가 더 빨리 온다.

02 · PROBLEMS

현재 파서의 문제점

현재 운영 중인 파서는 오랜 기간 누적된 구조적·운영적 부채를 안고 있다. 문제를 성격별로 6개 그룹으로 정리한다.

2.1단일 프로그램에 과집중된 책임
수집·삭제·표준/비표준 가공·Config까지 한 프로그램에 뒤섞여, 한 영역의 변경이 다른 영역으로 전파되고 전체 구조를 파악하기 어렵다.
2.2레거시 품질·유지보수·테스트 난이도
인수인계 미흡·저품질 레거시라 수정이 어렵고 복잡해지는 설비 대응에 한계가 있다. 테스트 코드가 없고 함수가 크며 추상화가 없어, 검증을 개인 경험에 의존한다.
2.3정규화·보정 로직의 산재
표준 로그도 결함이 많아 표현을 통일하는 정규화와 누락·오류를 고치는 보정이 필요하다. 전담 모듈 대신 가공 로직에 예외처리로 섞여 DB·보정·가공 모듈에 흩어져 있고, 관련 로직만 50종 이상이라 버그 추적이 어렵다.
2.4기준정보 설계·활용 미흡
기준정보의 DB 스키마 정규화가 부족해 한 테이블에 정보가 혼재하고 값 형식이 단일/리스트로 혼용된다. 활용 부분도 확장성이 없어 단순 수정에도 러닝커브가 존재한다.
2.5스케줄링·재처리·Carryover 수작업
범용·레거시 스케줄러라 파서에 맞게 수정하기 어렵고, 재처리·순차 가공 대응이 안 돼 사람이 DB를 직접 손댄다. 비표준 carryover·Config는 서버별 파일로 흩어져 운영이 더 복잡하다.
2.6성능·서버 자원 비효율
한 번에 전체 Job을 처리해 순간 피크로 AP·DB 서버 오류가 나고, 정적 thread 설정 기반이라 수동 조정이 필요하다. 피크 후 사용량 급감과 프로세스 간 작업량 불균형으로 효율이 낮다.

기준정보(DB) 개선

책임 분리와 함께 DB 기준정보 구조도 개선한다. 한 테이블에 혼재된 정보를 분리하고, 값 형식(단일/리스트)을 일관되게 맞추며, 파서의 기준정보 활용 부분이 확장 가능하도록 정리해 단순 수정 시의 러닝커브를 낮춘다.

가공 시나리오 — '수집'과 분리

세 시나리오의 차이는 "어떤 구간을 어떤 순서로 가공하느냐"일 뿐, "어떻게 수집하느냐"가 아니다. 따라서 시나리오는 가공의 축으로 두고 수집과 분리한다. 스케줄러가 원본 존재 여부를 먼저 확인하고, 있으면 바로 파서를, 없으면 그때 수집기를 호출한다.

Live
아직 가공되지 않은 최신 파일을 가져와 가공하는 운영의 기본 흐름.
Rework
특정 구간·타겟(공정·모델·메이커)에서 문제 발생 시 해당 부분만 재가공. 삭제·재적재 등 상세 정책은 별도 결정.
따라잡기
가공이 하루~이틀 밀렸을 때 전체를 하루 단위씩 순차 가공해 설비별 진행 속도를 고르게 맞춘다.
04 · NON-FUNCTIONAL

비기능적 개선 (운영·아키텍처)

기능 분리와 별개로, 파이프라인을 안정적·효율적으로 운영하기 위한 구조적 개선을 함께 추진한다.

4.1 상태의 중앙화 (SSOT)

설비별 진행 상황을 DB 테이블로 중앙 관리해 단일 진실 원천(SSOT)을 확보한다. 상태가 한곳에 모이면 "어디까지 처리했는지"를 항상 파악하고, 재처리·순차 가공을 스케줄러가 상태를 읽고 자동 수행하며, 파일로 흩어진 carryover·Config 상태도 흡수한다.

4.2 자원 활용 효율화 (부하 평준화)

순간 피크로 서버가 오류 나던 구조를, 부하를 시간에 고르게 분산하는 구조로 바꾼다. 전체 Job을 1시간 내 배치로 나눠 피크를 없애되 설비별 최소 1회/시간 가공을 보장하고, 정적 thread 대신 실시간 CPU 기반으로 동적 분배한다.

1시간 동안의 서버 사용량 — 한 번에 몰아 처리 vs 배치 분산
AS-IS순간 피크 → 서버 오류
TO-BE고르게 분산 → 안정
4.3 스케줄러 내부 책임의 계층화

스케줄러는 역할이 큰 만큼 내부 책임이 한 덩어리로 비대해지지 않도록 개념적으로 층을 나눈다. 과거 파서가 겪은 "한 곳에 책임 과집중" 문제를 스케줄러가 반복하지 않기 위함이다. 정책과 메커니즘을 분리하면 한쪽(분배 알고리즘)을 바꿔도 다른 쪽(시나리오 규칙)에 영향을 주지 않는다.

상태 계층
진행 상황을 DB 테이블을 SSOT로 둔다. 스케줄러는 읽고 쓰는 주체일 뿐, 상태를 자체 보유하지 않는다.
정책 계층 무엇을
시나리오(live/rework/따라잡기) 판단, 처리할 파일 구간 산정 등 "결정" 로직.
메커니즘 계층 어떻게/언제
CPU 사용량 기반 분배, 배치 타이밍 등 "실행" 로직(4.2 자원 효율화와 직결).
05 · TESTING

테스트 전략

신규 구조를 별도로 구축한 뒤 핵심 가공 경로부터 단계적으로 전환한다. 변화가 시급해 일정 부작용은 감수하되, 그 리스크를 "인지하고 통제"하기 위해 다음 전략을 둔다.

5.1 골든 파일(동등성) 테스트 — 전환 검증의 핵심

실제 로그 파일을 입력으로, 기존 파서 출력과 새 시스템(컨버터+표준파서) 출력을 나란히 비교(diff)한다. 의도한 차이만 있고 의도치 않은 차이는 없는지를 검증하는 안전망. 코드 품질과 무관하게 입출력만으로 구성 가능해 즉시 도입할 수 있다.

5.2 raw 데이터 품질 평가 활용
별도 계획 중인 raw 데이터 품질 평가 방법론으로 가공 결과 품질을 정량 검증한다. 단순 출력 비교를 넘어 데이터가 기대 품질 기준을 충족하는지 확인한다.
5.3 신규 컴포넌트 단위 테스트
컨버터·표준 파서·Config 파서를 처음부터 테스트 가능한 구조(작은 함수·의존성 주입)로 설계하고 단위 테스트를 함께 작성해, 레거시의 구조적 문제를 설계 단계에서 예방한다.
5.4 정규화·보정의 데이터 기반 테스트
보정 로직이 50종 이상이라 케이스마다 코드를 쓰기보다 (입력, 기대 출력) 쌍을 데이터로 관리하는 파라미터화 테스트를 적용한다. 케이스가 늘어도 데이터만 추가하면 된다.
5.5 (옵션) 병행 운영 · 5.6 CI 연동
환경이 허락하면 정식 반영 전 같은 입력을 백그라운드로 함께 처리해 비교하는 Shadow Run을 짧게 거치고, 위 테스트들을 CI에 연동해 검증을 자동화한다.
06 · OUTCOME

08 · SCOPE & OPEN ITEMS

범위 및 단계 계획

한 번에 전체를 완성하기보다, 데이터가 끝까지 흐르는 최소 기능(MVP)을 올해 먼저 확보하고 이후 단계적으로 고도화한다.

올해 (MVP)

"비표준 로그 → 표준화 → 가공" 데이터 흐름을 최소 형태로 끝까지 잇는다. 핵심은 가공 로직(컨버터+표준파서)의 신규 구축·검증이며, 스케줄러·수집기는 이를 구동할 최소한으로 한정한다.

REFERENCE

용어 정의 — 참고

문서에서 사용하는 용어의 간단 정의. 본문 흐름에 필요할 때만 참고한다.

표준 로그 스펙 — 회사 내부 표준 로그 양식. 설비사에 전달해 이 양식대로 로그를 생성하도록 요청.
표준 / 비표준 로그 — 표준 스펙 준수 로그(TSV) vs 설비사 자체 양식 로그(변환 필요).
기타 Configuration — 설비 파라미터 등 표준/비표준 외 별도 파일. 설비사별 양식 상이.
DB / AP 서버 — DB는 데이터·기준정보 보유·여러 AP 관리, AP는 설비 접근·수집·적재.
스케줄러 Job / 로그상 Job — 파서가 처리할 설비 단위 작업 vs lot이 설비에서 진행하는 작업 단위.
레거시 스케줄러 — Job 리스트를 받아 각 프로세스에 분배하는 범용 모듈.
Carryover — 시간 단위로 쪼개진 파일 경계에서 다음 파일로 넘겨야 하는 미완료 동작·흐름 정보.
로그 값 정규화 — 설비사·모델별 제각각 표현(alias·코드·모듈타입)을 같은 기준으로 정렬.
DB 스키마 정규화 — 기준정보 테이블의 중복·혼재, 단일/리스트 혼용 등 구조 정리.
보정 (Correction·Enrichment) — 로그 결함을 메움: 누락 보강 + 오류 수정. 정규화와 별개 단계.
단계별 전환 — 핵심 경로를 먼저 신규 구축·검증 후 단계적으로 고도화하는 전환 방식.
