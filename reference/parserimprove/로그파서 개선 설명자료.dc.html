로그파서 개선 프로젝트

설비가 실시간으로 남기는 방대한 로그를, 사람이 분석·활용할 수 있는 정형 데이터로 바꿔 주는 핵심 데이터 파이프라인. 오랜 운영으로 누적된 구조적·운영적 부채를 점진 수선하는 대신, 책임이 명확히 분리된 새 구조로 재설계하여 장기적인 유지보수성·확장성·운영 효율을 확보한다.

본 문서는 승인 요청서가 아니라, 실무자가 실제로 어떤 방향으로 개선을 진행할지 설명하기 위한 실행 방향 공유 자료이다. 전체 구조는 개요 수준으로 설명하되, 상세 실행 범위는 올해 MVP를 중심으로 정리한다.

00 · GLOSSARY

용어 정의

문서 전반에서 사용하는 핵심 용어를 먼저 정리한다. 특히 표준/비표준 로그, 스케줄러 Job vs 로그상 Job, 정규화 vs 보정은 이후 설명의 기준이 되므로 구분이 중요하다.

표준 로그 스펙
회사 내부에서 정한 표준 로그 양식. 설비사에 전달해 설비가 이 양식대로 로그를 생성하도록 요청한다. 동작 start/end, 로봇·공정·랏 진행·설비 function·파라미터 등 설비 전반 정보를 담는다.
표준 로그
표준 스펙을 준수해 생성된 로그. TSV 형식의 txt 파일로 저장되며, 시간 단위로 압축 보관된다.
비표준 로그
설비사가 자체 양식으로 생성하는 실시간 로그. 설비사마다 형식이 달라, 활용 가능한 데이터로 만들려면 별도 변환 로직이 필요하다.
기타 Configuration
설비 파라미터 등 표준/비표준 로그 외 정보를 담은 별도 파일. 역시 설비사별로 양식이 달라 각각 별도 로직으로 가공해야 한다.
DB 서버 / AP 서버
DB 서버는 데이터·기준정보를 보유하며 여러 AP 서버를 관리한다. AP 서버는 실제 앱이 실행되는 서버로, 설비에 접근해 로그를 수집하고 파서가 가공한 데이터를 담당 공정 DB 서버에 적재한다.
스케줄러 Job / 로그상 Job
스케줄러 Job은 파서가 처리해야 하는 설비 단위 작업. 로그상 Job은 로그 내용상 하나의 lot이 설비에서 진행하는 작업 단위로, 의미가 다르므로 구분해 사용한다.
레거시 스케줄러
DB 서버로부터 해당 AP 서버에 맞는 스케줄러 Job(가공할 설비 정보 리스트) 전체를 받아 각 프로세스에 분배하는 모듈.
Carryover
로그 파일이 시간 단위로 분리되어 start와 end가 다른 파일에 나뉠 수 있다. 다음 파일 가공 시점에 전달해야 하는 이전 파일의 미완료 동작·흐름 정보를 뜻한다.
로그 값 정규화 Value Normalization
설비사·모델마다 제각각인 표현(alias, 코드 체계, 모듈 타입 등)을 일관된 표준 형태로 통일하는 단계. "틀린 것을 고친다"보다 "제각각인 것을 같은 기준으로 정렬한다"에 가깝다.
DB 스키마 정규화 DB Normalization
기준정보 테이블의 중복·혼재를 줄이고, 단일 값/리스트 혼용 등 구조적 문제를 정리하는 DB 설계 관점의 정규화.
보정 Correction · Enrichment
로그 자체의 결함을 메우는 단계. 흐름 추적으로 누락된 정보를 채우고(보강), 잘못된 값을 교정(수정)한다. 로그 값 정규화와는 층위가 다른 별개 단계다.
단계별 전환
레거시를 한 번에 교체하기보다, 핵심 가공 경로를 먼저 신규 구조로 구축·검증하고 이후 운영 기능을 단계적으로 고도화하는 전환 방식.
01 · BACKGROUND

배경 및 개요

설비 이벤트 로그파서는 단순히 동작 단위로 로그를 묶는 도구가 아니다. 설비·랏·웨이퍼의 전반적 흐름을 추적하여 각 로그에 부족한 정보를 채우거나 여러 로그를 합쳐 새로운 정보를 생성한다. 표준 로그 스펙이 완벽하지 않고 설비사별 로그 품질 차이가 존재하기 때문이다. 실시간 로그는 동작 시작(start)과 종료(end)가 서로 다른 라인으로 기록되므로, 파서는 이를 합쳐 하나의 분석 가능한 데이터로 만든다. 이 데이터가 이후 통계·분석의 기반이 되므로 파서의 안정성과 정확성은 곧 후속 데이터 전반의 신뢰도와 직결된다.

추진 배경 — 현재 파서가 부딪힌 한계

구조적 한계
수집·삭제·표준/비표준 가공·Config 처리 등 성격이 다른 역할이 한 프로그램에 뒤섞이고, 정규화·보정 로직마저 여러 곳에 흩어져 유지보수와 버그 추적이 어렵다.
레거시 부채
인수인계가 미흡한 저품질 레거시 코드에 테스트 코드까지 없어, 수정과 배포가 개인의 경험에 크게 의존한다.
운영 부담
재처리·따라잡기 등 운영 시나리오를 자동 처리하지 못해 수작업과 실수가 잦고, 순간 부하 피크로 서버 오류가 발생하는 등 자원 활용이 비효율적이다.
변화하는 요구
설비 동작과 로그가 갈수록 복잡해지는데, 현재 구조로는 이를 따라가기 어렵다. 부채를 방치하면 대응 한계가 더 빨리 찾아온다.

02 · PROBLEMS

현재 파서의 문제점

현재 운영 중인 파서는 오랜 기간 누적된 구조적·운영적 부채를 안고 있다. 문제를 성격별로 6개 그룹으로 정리한다.

2.1단일 프로그램에 과집중된 책임
설비 접근·로그 수집, 오래된 파일 삭제, 표준·비표준 가공, 기타 Config 가공까지 성격이 다른 작업이 한 프로그램에 뒤섞여 있다. 책임이 분리되지 않아 한 영역의 변경이 다른 영역에 영향을 주기 쉽고, 전체 구조를 파악하기 어렵다.
2.2레거시 품질·유지보수·테스트 난이도
비표준·기타 처리 로직은 인수인계가 미흡하고 코드 품질이 낮아 수정이 어렵다. 복잡해지는 설비에 대응이 한계에 부딪히고, 테스트 코드가 없어 검증을 개인 경험에 의존한다. 함수가 크고 추상화가 없어 구조 자체가 테스트에 부적합하다.
2.3정규화·보정 로직의 산재
표준 로그라도 결함이 많아, 표현을 통일하는 정규화와 누락·오류를 고치는 보정이 필요하다. 이상적으로는 전담 모듈이 담당해야 하나, 실제로는 가공 로직 안에 예외처리로 섞여 DB·보정·가공 모듈에 흩어져 있다. 관련 로직은 합쳐 50종 이상이라 버그 원인 추적이 어렵다.
2.4기준정보 설계·활용 미흡
설비/모델/공정 매핑, alias·모듈 타입 등 기준정보의 DB 스키마 정규화가 부족하다. 한 테이블에 여러 정보가 혼재하고 값 형식이 단일/리스트로 혼용되는 제1정규형 수준 문제가 있다. 활용 부분도 확장성을 고려하지 않아 단순 수정에도 러닝커브가 존재한다.
2.5스케줄링·재처리·Carryover 수작업
현재 스케줄러는 파서 전용이 아닌 범용·레거시라 적합하게 수정하기 어렵다. 재처리·하루치 순차 가공 등 시나리오 대응이 어려워 사람이 DB를 직접 수정·삭제한다. 비표준 carryover는 파일로 관리되어 원격 접속해 직접 삭제해야 하고, Config도 서버별 파일로 흩어져 운영 변경이 더 어렵다.
2.6성능·서버 자원 비효율
한 번 돌 때 전체 Job을 한꺼번에 처리해 순간 부하 피크로 AP·DB 서버 오류가 난다. 부하 제어가 정적 thread 설정값 기반이라 서버마다 수동 조정이 필요하고, 피크 후 사용량이 급감해 자원 효율이 낮다. 프로세스 간 작업량 불균형으로 일부는 일찍 끝나고 일부는 계속 도는 비효율도 크다.
03 · DIRECTION

개선 방향 — 책임 분리

하나의 프로그램에 뭉쳐 있는 역할을, 명확한 책임을 가진 독립 프로그램으로 분리한다. 각 컴포넌트를 독립적으로 수정·배포·테스트할 수 있게 하고, 전체 파이프라인 흐름을 한눈에 파악·제어할 수 있도록 한다.

DB 서버 — 데이터 · 기준정보 · 진행상황 상태(SSOT) · 스케줄러와 양방향, CPU 사용량 참고
① 스케줄러
전체 파이프라인을 조정하는 컨트롤 타워. 시나리오에 맞는 파일 구간을 정해 수집기·파서·컨버터를 호출하고 필요한 DB 업데이트를 수행한다. 설비별 진행 상태를 DB로 관리하고, 실시간 CPU 사용량을 직접 확인해 Job을 동적으로 분배한다. 1시간 내 전체 Job을 적절한 간격의 배치로 나눠 순간 피크 없이 자원을 고르게 쓴다.
② 파일 수집기
설비에서 로그 파일을 다운로드하고, 오래된·stale 파일을 삭제한다. Config 같은 스냅샷 파일은 날짜·수정 시점별로 정리하고, 해시값으로 실제 변경 시점에만 가져온다. "원본을 확보하고 가용성을 알리는" 역할만 가지며, 그 파일이 live/rework 중 어디에 쓰이는지는 알지 않는다(가공 시나리오와 독립).
③ 표준 로그 파서
표준 로그만 가공한다. 도메인 내부에 정규화·보정·start/end 병합 등 하위 모듈을 분리 배치한다. 외부에서는 하나의 표준 파서로 호출되지만, 내부적으로는 단계별 책임을 나눠 관리한다.
④ 컨버터
비표준 로그를 표준 스펙 형식으로 변환한다. 최종 목표는 모든 가공을 표준 파서 하나로 일원화하는 것 — 비표준도 컨버터를 거쳐 표준 형식이 되면 동일 파서로 처리된다. 기존 비표준 파서 레거시를 좋은 품질의 컨버터로 새로 만든다.
⑤ 추가 Configuration 파서
표준/비표준 로그와 성격이 다른 파일을 별도 파서로 분리한다. 현재는 Config 로직만 고쳐도 전체를 재배포해야 해 정상 동작 중인 파서까지 배포 리스크에 노출된다. 분리하면 변경 영향 범위 격리, 배포 리스크·빈도 감소, 독립적 테스트·롤백이 가능해진다.

기준정보(DB) 개선

책임 분리와 함께 DB 기준정보 구조도 개선한다. 한 테이블에 혼재된 정보를 분리하고, 값 형식(단일/리스트)을 일관되게 맞추며, 파서의 기준정보 활용 부분이 확장 가능하도록 정리해 단순 수정 시의 러닝커브를 낮춘다.

가공 시나리오 — '수집'과 분리

세 시나리오의 차이는 "어떤 구간을 어떤 순서로 가공하느냐"일 뿐, "어떻게 수집하느냐"가 아니다. 따라서 시나리오는 가공의 축으로 두고 수집과 분리한다. 스케줄러가 원본 존재 여부를 먼저 확인하고, 있으면 바로 파서를, 없으면 그때 수집기를 호출한다.

Live
아직 가공되지 않은 최신 파일을 가져와 가공하는 운영의 기본 흐름.
Rework
특정 구간·타겟(공정·모델·메이커)에서 문제 발생 시 해당 부분만 재가공. 삭제·재적재 등 상세 정책은 별도 결정.
따라잡기
가공이 하루~이틀 밀렸을 때 전체를 하루 단위씩 순차 가공해 설비별 진행 속도를 고르게 맞춘다.
04 · NON-FUNCTIONAL

비기능적 개선 (운영·아키텍처)

기능 분리와 별개로, 파이프라인을 안정적·효율적으로 운영하기 위한 구조적 개선을 함께 추진한다.

4.1 상태의 중앙화 (SSOT)

설비별 파이프라인 진행 상황을 DB 테이블로 중앙 관리해 단일 진실 원천을 확보한다. 현재는 상태가 DB·파일·AP 서버에 흩어져 수작업·실수가 잦았다. 한곳에 모으면 "어디까지 처리했는지"를 항상 파악하고, 재처리·하루치 순차 가공을 사람이 아닌 스케줄러가 상태를 읽고 자동 수행하며, 파일로 흩어진 비표준 carryover·Config 상태도 가능한 범위에서 중앙 관리로 흡수한다.

4.2 자원 활용 효율화 (부하 평준화)

순간 피크로 서버가 오류 나던 구조를, 부하를 시간에 걸쳐 고르게 분산하는 구조로 전환한다. 전체 Job을 1시간 내 적절한 간격의 배치로 나눠 순간 피크를 없애되, 설비 단위로는 최소 한 시간에 한 번 가공을 보장한다. 정적 thread 설정값 대신 스케줄러가 실시간 CPU 사용량을 보고 동적으로 분배한다(기존 CPU 측정 프로그램 재사용).

4.3 스케줄러 내부 책임의 계층화

스케줄러는 역할이 큰 만큼 내부 책임이 한 덩어리로 비대해지지 않도록 개념적으로 층을 나눈다. 과거 파서가 겪은 "한 곳에 책임 과집중" 문제를 스케줄러가 반복하지 않기 위함이다. 정책과 메커니즘을 분리하면 한쪽(분배 알고리즘)을 바꿔도 다른 쪽(시나리오 규칙)에 영향을 주지 않는다.

상태 계층
진행 상황을 DB 테이블을 SSOT로 둔다. 스케줄러는 읽고 쓰는 주체일 뿐, 상태를 자체 보유하지 않는다.
정책 계층 무엇을
시나리오(live/rework/따라잡기) 판단, 처리할 파일 구간 산정 등 "결정" 로직.
메커니즘 계층 어떻게/언제
CPU 사용량 기반 분배, 배치 타이밍 등 "실행" 로직(4.2 자원 효율화와 직결).
05 · TESTING

테스트 전략

신규 구조를 별도로 구축한 뒤 핵심 가공 경로부터 단계적으로 전환한다. 변화가 시급해 일정 부작용은 감수하되, 그 리스크를 "인지하고 통제"하기 위해 다음 전략을 둔다.

5.1 골든 파일(동등성) 테스트 — 전환 검증의 핵심

실제 로그 파일을 입력으로, 기존 파서 출력과 새 시스템(컨버터+표준파서) 출력을 나란히 비교(diff)한다. 의도한 차이만 있고 의도치 않은 차이는 없는지를 검증하는 안전망. 코드 품질과 무관하게 입출력만으로 구성 가능해 즉시 도입할 수 있다.

실제 로그 파일
→
기존 파서 → 출력 A
신규(컨버터+표준파서) → 출력 B
→
diff 비교
의도한 차이만 존재?
5.2 raw 데이터 품질 평가 활용
별도 계획 중인 raw 데이터 품질 평가 방법론으로 가공 결과 품질을 정량 검증한다. 단순 출력 비교를 넘어 데이터 자체가 기대 품질 기준을 충족하는지 확인해 전환 신뢰도를 높인다.
5.3 신규 컴포넌트 단위 테스트
컨버터·표준 파서·Config 파서를 처음부터 테스트 가능한 구조(작은 함수, 의존성 주입)로 설계하고 단위 테스트를 함께 작성한다. 레거시의 구조적 문제를 설계 단계에서 예방한다.
5.4 정규화·보정의 데이터 기반 테스트
보정 로직이 50종 이상이므로 케이스마다 코드를 쓰기보다 (입력 로그, 기대 출력) 쌍을 데이터로 관리하는 파라미터화 테스트를 적용한다. 케이스가 늘어도 데이터만 추가하면 된다.
5.5 (옵션) 병행 운영 · 5.6 CI 연동
환경이 허락하면 정식 반영 전 같은 입력을 백그라운드로 함께 처리해 결과를 비교하는 Shadow Run을 짧게 거친다. 위 테스트들을 CI에 연동해 개인 경험 의존 검증을 자동화된 검증으로 대체한다.

07 · RISK

리스크 및 완화 방안

단계별 전환과 레거시 이관이라는 특성상 다음 리스크가 존재한다. 변화가 시급해 일정 부작용은 감수하되, 아래와 같이 통제한다.

전환 시 동등성 깨짐
새 시스템이 기존과 다른 결과를 내 후속 통계·분석에 영향. → 골든 파일 테스트로 의도치 않은 차이 검출, raw 품질 평가, 가능 시 병행 운영.
정규화·보정 로직 이관 누락
50종 이상 로직 이관 중 일부 케이스 누락·변형. → 데이터 기반 테스트로 케이스화하여 누락 시 즉시 검출.
전환 중 운영 공백·호환 문제
신규·레거시 경로 공존 기간의 중단·장애·호환 문제. → 충분한 사전 검증, 롤백 경로 확보, 가능 시 병행 운영 비교.
레거시 사양 미문서화
인수인계 미흡으로 숨은 동작·예외처리가 명세화 안 됨. → 골든 테스트로 실제 입출력을 기준 삼아 동작을 역으로 고정·문서화.
신규 스케줄러 복잡도
스케줄러에 역할이 집중되어 새 복잡도 유발 가능. → 정책·메커니즘·상태 계층 분리(4.3)로 내부 책임 구획화.
일정 리스크 · 재처리 중복·누락
신규 구축+전환 지연, rework 시 중복 적재·누락 가능. → 핵심 경로 중심 MVP로 범위 축소, rework 정책·재적재 방식을 테스트 케이스에 포함.
08 · SCOPE & OPEN ITEMS

범위 및 단계 계획

한 번에 전체를 완성하기보다, 데이터가 끝까지 흐르는 최소 기능(MVP)을 올해 먼저 확보하고 이후 단계적으로 고도화한다.

올해 (MVP)

"비표준 로그 → 표준화 → 가공" 데이터 흐름을 최소 형태로 끝까지 잇는다. 핵심은 가공 로직(컨버터+표준파서)의 신규 구축·검증이며, 스케줄러·수집기는 이를 구동할 최소한으로 한정한다.

스케줄러최소 기능만

차후 (고도화)
  • 스케줄러 고도화 — rework·따라잡기 오케스트레이션, 상태 중앙화(SSOT), 동적 CPU 분배·배치 평준화
  • 파일 수집기 고도화 — 오래된/stale 정리, Config 스냅샷 관리, 해시 변경 감지, 재수집 명령
  • 추가 Config 파서 — 표준/비표준과 분리된 별도 파서로 구축
  • 기준정보(DB) 개선 — 스키마 정규화 및 활용 구조 개선
  • 테스트·운영 체계 확장 — 병행 운영(shadow run), CI 연동

미정사항 및 추가 검토 필요
