REVIEW · 지침 개선 검토

FeedbackOps 브리프 문제의 재발 방지 리뷰

이 문서는 FeedbackOps 발표 자료에서 발견된 문제를 원본 프로젝트의 지침·스킬·검증 게이트로 얼마나 예방할 수 있는지 정리한다. 모바일 대응은 범위에서 제외하고, 회사 PC에서 보는 desktop-only 문서를 전제로 한다.

1. 결론

지침이 없어서 생긴 문제는 아니다 한 섹션 한 논지, 무게중심 하나, 도식 가능한 내용은 도식화한다는 규칙은 이미 있다.
강제 장치가 약했다 작성 전 preflight와 작성 후 gate가 없어 기존 규칙을 어긴 상태로도 통과했다.
도식 선택표는 보강 필요 분기 workflow, ownership matrix, UI surface, relationship schema 같은 케이스는 더 명확해야 한다.

2. 지침 문제가 아닌 부분

섹션 역할 과다

s1은 before/after, use case, executive point를 한 섹션에 담고, s5는 workflow, 상태, rule, use case를 함께 담는다. 기존 composition guide만 제대로 적용했어도 걸러졌을 문제다.

카드형 구조 남발

카드가 보기 좋게 정리되었지만, 실제로는 관계·분기·소유권을 보여줘야 하는 곳에서 카드가 도식을 대체했다. 이는 지침 부재라기보다 "더 넣어줘" 요청을 append 방식으로 처리한 실행 문제에 가깝다.

의사결정 요청이 늦게 등장

결정 요청은 마지막 MVP 섹션의 작은 카드에 들어갔다. 결정권자 설득이 목표라면 opening 또는 별도 decision block으로 올라와야 한다.

3. 실제로 보강할 지점

내용 형태 써야 할 도식 피해야 할 표현 검토 질문
분기·승인·반려·재요청이 있는 workflow UML activity 또는 swimlane 단순 process row 모든 종료·반복 상태가 보이는가?
도메인 객체별 소유 경계 matrix 동일 가중 카드 행과 열이 서로 다른 의미를 운반하는가?
시스템과 선택적 integration layer layered architecture map 단순 트리 박스 소유권·선택성·연결선이 보이는가?
역할별 UI 사용 방식 surface map 또는 lane map 원칙 카드만 나열 화면·행동·handoff가 역할별로 보이는가?
의사결정 요청 decision block 또는 open-question table 작은 peer card 결정 요청을 놓칠 수 없게 보이는가?

4. 작성 프로세스에 추가할 게이트

  1. HTML 작성 전에 narrative lens를 선언한다: architecture-first, use-case-first, decision-first.
  2. 섹션마다 page type, claim type, primary device, figure budget을 적는다.
  3. 사용자가 내용을 더 넣으라고 하면 append하지 말고 core/support/aside로 분류한다.
  4. core면 섹션을 분할하거나 outline을 바꾼다. support만 기존 섹션에 남긴다.
  5. 결정 요청은 peer card가 아니라 decision block 또는 Scope/Plan open-question table에 둔다.

5. 애매할 때 물어볼 질문

  • 이 문서는 결정권자를 먼저 설득해야 하는가, use case를 먼저 보여줘야 하는가, architecture를 먼저 설명해야 하는가?
  • "use case 중심"은 전체 outline을 actor/scenario 중심으로 재구성하라는 뜻인가, 기존 구조에 예시만 추가하라는 뜻인가?
  • 의사결정 요청은 최종 승인 요청인가, 열린 질문 목록인가, 은근한 추천인가?
  • "더 자세히"는 같은 섹션을 깊게 하라는 뜻인가, 새 섹션을 만들라는 뜻인가, 낮은 가치의 개요를 구체 사례로 바꾸라는 뜻인가?
  • 이미 도식이 있는 섹션에 새 정보가 들어오면 도식을 교체해야 하는가, 새 섹션으로 빼야 하는가, appendix로 내려야 하는가?

6. 검증 게이트 개선

현재 verify-doc.mjs는 구조 검증 중심이라 composition 실패를 잡지 못한다. desktop 기준 visual/composition tier를 warning부터 추가하는 것이 맞다.

  • 1366x768, 1440x900 캡처를 남긴다.
  • 한 섹션에 grid가 3개 이상 쌓이면 경고한다.
  • figure panel 안에 서로 다른 카드 묶음이 여러 개 있으면 경고한다.
  • workflow, map, matrix, state, surface라는 계획어가 있는데 실제 주 도식이 없으면 경고한다.
  • decision ask가 낮은 강조의 peer card에만 있으면 경고한다.

요약

좋은 해결책은 "더 예쁘게"가 아니라, 작성 루프를 강화하는 것이다. lens 선언 → 섹션 preflight → 강화된 도식 mapping → 내용 추가 시 재배치 판단 → desktop composition 검증 순서가 필요하다.
